                  Nibble-Aligned LZ Compression (Lamarr)
                          Format Specification

                              Version 1.0

          Clean-room reimplementation of the LZMAT compression
            algorithm originally designed by Vitaly Evseenko.
              Reference implementation by John "k0u74ku" Doe


Abstract

    This document specifies a nibble-aligned LZ-style lossless
    compression format. The format operates on an octet stream,
    producing a self-delimiting compressed representation through a
    tag-byte-driven state machine. A literal octet is emitted as-is;
    a backward reference (match) is encoded as a distance-length pair
    using variable-width fields whose bit alignment shifts at nibble
    granularity.

    The specification covers both the compressed bitstream grammar and
    the file-level container used by the self-extracting stub loader.


1.  Conventions and Terminology

    The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL
    NOT", "SHOULD", "SHOULD NOT", "RECOMMENDED", "MAY", and
    "OPTIONAL" in this document are to be interpreted as described in
    RFC 2119.

    Bit numbering follows the least-significant-bit-first convention:
    bit 0 is the least significant bit of an octet. Multi-octet values
    are stored in little-endian byte order.

    Notation:

        u8       Unsigned 8-bit integer (octet).
        u16      Unsigned 16-bit little-endian integer.
        u32      Unsigned 32-bit little-endian integer.
        nib      Cursor within an octet:  0 = low nibble
                 (bits 3:0), 1 = high nibble (bits 7:4).
        outPos   Current write position in decompressed output,
                 zero-based.
        inPos    Current read position in the compressed input,
                 zero-based.  inPos = 0 holds the initial octet;
                 inPos = 1 is the first tag byte (Section 3.1).
        tag      The current tag byte (see Section 3.2).

    The term "nibble-aligned" refers to a read or write operation
    that begins at an arbitrary nibble boundary rather than an octet
    boundary.


2.  Bitstream Layer

2.1.  Nibble Alignment

    All bitstream values are written and read with nibble alignment.
    A cursor tracks whether the next operation begins at the low
    nibble (nib = 0) or high nibble (nib = 1) of the current octet.

    Formally, to read a u8 value v from octet stream S at position p
    with nibble state nib:

        if nib = 0:
            v := S[p]
            p := p + 1
        if nib = 1:
            v := (S[p] >> 4) | (S[p + 1] << 4)
            p := p + 1

    The cursor advances by one octet after each read.

    For writing, the encoder toggles nib on U4, LE12, and LE20 write
    operations. U8 and LE16 writes do not toggle nib. Consecutive
    nibble-aligned writes share output octets: the first write occupies
    the low nibble of an octet and the second occupies the high nibble,
    at which point the cursor advances to the next octet.

    The encoder write primitives are specified in Section
    5.3. The nibble toggle behaviour of each primitive is specified
    individually.

2.2.  Multi-Byte Little-Endian Reads

    Wider fields (12-bit, 16-bit, 20-bit) are read as native LE
    integers and then masked. Reads past end-of-buffer return zero
    for missing octets, allowing the decoder to consume padding bits
    at stream end without explicit markers.

        u20  = (u32 >> 4) & 0xFFFFF   if nib = 1
                u32       & 0xFFFFF   if nib = 0

        u16  = (u32 >> 4) & 0xFFFF    if nib = 1
                u16       & 0xFFFF    if nib = 0

        u12  = (u16 >> 4) & 0xFFF     if nib = 1
                u16       & 0xFFF     if nib = 0

    The u20 read consumes 4 octets but advances the cursor by 1.
    The u12 read consumes 2 octets; cursor advance is caller-handled
    (see Section 4.2).
    The u16 read used for length extension (Section 4.2) consumes
    4 octets when nib = 1 (reading a u32 and shifting) and 2 octets
    when nib = 0.


3.  Compressed Stream Grammar

    top-level     := INITIAL_OCTET item*
    item          := literal | match
    literal       := RAW_OCTET
    match         := distance length

3.1.  Initial Byte

    The first octet of the original input MUST be copied verbatim to
    the first octet of the compressed output. This establishes the
    output origin for backward references. Both cursors are then
    initialised to 1:  inPos = 1 (first tag byte) and outPos = 1
    (first output position already filled by the initial copy).

3.2.  Tag Byte

    A tag byte is a u8 value encoding the type of the next 1 to 8
    items. Bit 7 (0x80) controls the first item, bit 6 the second,
    and so forth.

        bit = 0  =>  literal byte follows
        bit = 1  =>  match (distance + length) follows

    After 8 bits are consumed, a new tag byte is read. When fewer
    than 8 items remain in a tag group, unused bits MUST be set to 1.
    The decoder treats these as match items; boundary checks prevent
    spurious output (Section 3.5).

3.3.  Literal Byte

    A single raw octet, read with nibble alignment per Section 2.1,
    emitted directly to output.

3.4.  Match Item

    A match item represents a substring already present in the
    output. It consists of two sub-fields:

        distance    d such that source position is (outPos - d).
                    Encoded per Section 4.1.

        length      L >= 3 octets to copy.
                    Encoded per Section 4.2.

    The decompressor copies L octets from (outPos - d) to the current
    output position, advancing outPos by L.

3.5.  Stream Termination

    The decompressor halts when outPos reaches the expected
    decompressed size, or when the compressed input is exhausted
    (cursor at end of buffer, accounting for current nibble
    alignment).

    When either error condition below occurs, the decoder MUST halt
    and report an error; it MUST NOT attempt to continue decoding.

    Error conditions:

        (a)  Distance exceeds output:  d > outPos.
        (b)  Output buffer overflow:  outPos + L > expected size.

3.6.  Tag Byte Nibble Alignment

    The tag byte itself is subject to nibble alignment. When nib = 1
    (the previous write stopped mid-octet, so the current octet's
    high nibble is still unused), the tag is split across two octets:
    its low nibble occupies the high nibble of the current octet
    (OR'd with residual data), and its high nibble occupies the low
    nibble of the following octet. To avoid residual garbage, the
    encoder MUST zero the following octet before writing the tag.
    When nib = 0, the tag is written as a whole octet at the current
    output position, which then advances by one.


4.  Match Encoding

4.1.  Distance Coding

    A raw 20-bit field (cflag, u20 per Section 2.2) is read; the
    cursor advances by 1 octet. The coding tier is selected by
    outPos.

4.1.1.  Short Distance  (outPos < 0x881)

        cflag(0) = 0:
            d := ((cflag >> 1) & 0x7F)  + 1          // [1, 128]

        cflag(0) = 1:
            d := ((cflag >> 1) & 0x7FF) + 0x81       // [129, 2176]
            Cursor += nib; nib ^= 1.

4.1.2.  Long Distance  (outPos >= 0x881)

        cflag(1:0) = 00:
            d := ((cflag >> 2) & 0x3F)    + 1        // [1, 64]

        cflag(1:0) = 01:
            d := ((cflag >> 2) & 0x3FF)   + 0x41     // [65, 1088]
            Cursor += nib; nib ^= 1.

        cflag(1:0) = 10:
            d := ((cflag >> 2) & 0x3FFF)  + 0x441    // [1089, 17472]
            Cursor += 1.

        cflag(1:0) = 11:
            d := ((cflag >> 2) & 0x3FFFF) + 0x4441   // [17473, 279616]
            Cursor += 1 + nib; nib ^= 1.

    The fourth bucket requires L >= 4. If an encoder finds a match
    of length 3 whose distance falls in this bucket, it MUST encode
    the first octet as a literal and let the remaining two octets be
    handled by subsequent loop iterations. (The encoder cannot
    simply force L = 4, as that would copy an incorrect fourth octet
    from the source position.)

4.2.  Length Coding

    A raw 12-bit field (u12, Section 2.2) is read; after the read,
    Cursor += nib; nib ^= 1. The three cases are nested, and the
    Cursor += 1 in the second tier applies to both of its
    sub-cases:

        (u12 & 0xF) != 0xF:
            L := (u12 & 0xF) + 3                      // [3, 17]

        (u12 & 0xF) == 0xF:
            Cursor += 1.

            u12 != 0xFFF:
                L := (u12 >> 4) + 0x12                // [18, 272]

            u12 == 0xFFF:
                Read E as u16 (Section 2.2).
                Cursor += 2.
                L := E + 0x111.                       // [273, 0x1010F]

    The value E = 0xFFFF produces L = uCnt2Byte (0x10110), which is
    a sentinel triggering a Copy Chunk (Section 4.3) instead of a
    normal match.

    The constants used above are uCnt1Byte := 0xFF + 0x12 (0x111)
    and uCnt2Byte := 0xFFFF + uCnt1Byte (0x10110).

4.3.  Copy Chunk  (Uncompressed Fallback)

    When L = uCnt2Byte, the item is an uncompressed data block. The
    length C (in units of 4-octet groups) is decoded from context:

        nib = 1:   C := ((octet[Cursor - 4] & 0xFC) << 5)
                   Cursor += 1; nib := 0.

        nib = 0:   C := (u16[Cursor - 5] & 0xFC0) << 1

        C := C + (tag & 0x7F) + 4
        C := C << 1

    The decompressor MUST validate that outPos + C * 4 does not
    exceed the expected decompressed size before copying (Section
    3.5). It then copies C * 4 octets directly from the compressed
    input to output, advancing both cursors by C * 4. This consumes
    the remaining bits of the current tag byte (inner loop break).


5.  Encoding Algorithm  (Informative)

5.1.  Hash Chain

    A hash table maps 4-octet sequences to their most recent
    positions.

        h(p) := (u16(p) + ((u32(p) >> 9) & 0xFFFF))
                & (iDictSize - 1)

    iDictSize is 0x8000 (32768 entries). Collisions chain through
    an auxiliary index array of the same size. The chain is
    traversed until a position before the search window is reached:

        start_pos := 0                       if p < uDistMax
        start_pos := p - uDistMax            otherwise

    The reference encoder uses uDistMax = 0x4443F (279615), one less
    than the maximum encodable long distance (Section 4.1.2).

5.1.1.  RLE Fast Path

    When cbIn - inPtr >= 4 AND
         (*(u32 *)(inPtr - 1)) == (*(u32 *)(inPtr)):
        matchLen := 4
        while remaining > 0 AND inPtr[matchLen] == inPtr[matchLen - 1]:
            matchLen++
        return matchLen

5.2.  Match Selection

    When multiple matches exist at a position:

        (a)  A longer match is always preferred.
        (b)  If the candidate is longer by exactly 1, accept it only
             when its distance satisfies the inequality of (c) or
             (d); a candidate longer by more than 1 is always
             accepted.
        (c)  When the input position is at least 0x881, prefer the
             match whose distance satisfies (d_old * 128) > d_new,
             as the distance coding overhead becomes significant.
        (d)  Otherwise, prefer when (d_old * 8) > d_new.

    The encoder MAY use a progressive 2-byte hash-chain filter
    (a 16-bit lookahead value) to reduce false-positive byte
    comparisons. This is an optimisation detail and does not affect
    the format.

5.3.  Nibble-Aligned Write Primitives

    Toggle column indicates whether the primitive modifies the nibble
    cursor.

    SET_U8(out, pos, nib, v)                              // toggle: NO

        if nib != 0:
            out[pos] := out[pos] OR (u8)(v << 4)   ; pos := pos + 1
            out[pos] := (u8)(v >> 4)
        else:
            out[pos] := (u8)v                       ; pos := pos + 1

    SET_U4(out, pos, nib, v)                              // toggle: YES

        nib := nib XOR 1
        if nib = 1:
            out[pos] := (u8)(v AND 0x0F)
        else:
            out[pos] := out[pos] OR (u8)(v << 4)   ; pos := pos + 1

    SET_LE12(out, pos, nib, v)                            // toggle: YES

        nib := nib XOR 1
        if nib = 1:
            out[pos] := (u8)v                       ; pos := pos + 1
            out[pos] := (u8)(v >> 8)
        else:
            out[pos] := out[pos] OR (u8)(v << 4)   ; pos := pos + 1
            out[pos] := (u8)(v >> 4)                ; pos := pos + 1

    SET_LE16(out, pos, nib, v)                            // toggle: NO

        if nib != 0:
            out[pos] := out[pos] OR (u8)(v << 4)   ; pos := pos + 1
            out[pos] := (u8)(v >> 4)                ; pos := pos + 1
            out[pos] := (u8)(v >> 12)
        else:
            out[pos] := (u8)v                       ; pos := pos + 1
            out[pos] := (u8)(v >> 8)                ; pos := pos + 1

    SET_LE20(out, pos, nib, v)                            // toggle: YES

        nib := nib XOR 1
        if nib = 1:
            SET_LE16(out, (u16)v)          // advances pos by 2
            out[pos] := (u8)(v >> 16)
        else:
            out[pos] := out[pos] OR (u8)(v << 4)   ; pos := pos + 1
            SET_LE16(out, (u16)(v >> 4))  // advances pos by 2

5.4.  Copy Chunk Trigger

    When the encoder detects that the compressed output for a segment
    exceeds the corresponding raw input size, it flushes the
    accumulated uncompressed data as a Copy Chunk (see Section 4.3).
    Let cbUCData denote the number of uncompressed octets accumulated
    since the start of the current uncompressed segment, and let
    segBase denote the input position at which that segment began.
    The encoder advances inPtr past the flushed region by setting
    inPtr := segBase + (cbUCData & ~7), then encodes the trailing
    cbUCData & 7 octets in subsequent iterations (see B.3). After
    the flush, a new uncompressed segment begins at the updated inPtr.


6.  Container Format

    The reference implementations define two containers for shipping a
    compressed payload beside its stub. Both embed a conforming LZMAT-
    compatible bitstream per Sections 1 through 5; other implementations
    MAY use a different container.

    6.1.  Managed stub (single-file bundle container)

        The stub is a .NET single-file executable (Lamarr.dll, deps.json,
        runtimeconfig.json embedded by dotnet publish). The container is
        inserted directly before the bundle header. The bundle marker is
        a 40-octet structure:  an 8-octet u64 LE header offset followed
        by a 32-octet signature. The packer patches the marker's header
        offset so the bundle header stays addressable:

        [stub data .. header_off] [Lamarr container] [bundle header]

        +-----------+-------------------------------+
        | Offset    | Content                       |
        +-----------+-------------------------------+
        | 0         | Stub executable data (H)      |
        | H         | Magic: "Lamarr!!" (8 octets)  |
        | H + 8     | Entry count (u32 LE)          |
        | H + 12    | Total original size (u32 LE)  |
        | H + 16    | Total compressed size (u32 LE)|
        | H + 20    | Entry table (20 octets each)  |
        |           |   nameLen, rawLen, compLen,   |
        |           |   compOff, reserved           |
        | ...       | Names (UTF-8, 4-aligned)      |
        | ...       | Compressed blocks (LZMAT)     |
        | file-end  | Bundle header                 |
        +-----------+-------------------------------+

        H is the bundle header offset; container length C =
        8 + 12 + 20*N + names_area + compressed_size, so the patched
        marker offset is H + C. compOff is relative to the first
        compressed block. Entries MUST be ordered with entry 0 as
        the main assembly and the remaining entries as managed
        dependencies collected from deps.json.

        Magic octets:  0x4C 0x61 0x6D 0x61 0x72 0x72 0x21 0x21

        Loaders MUST scan backwards from end-of-file for the magic and
        validate: 1 <= entry count <= 4096, sizes positive, entry table
        and compressed blocks within the file.

        The stub MUST be a Windows executable whose runtimeconfig
        declares Microsoft.WindowsDesktop.App with rollForward
        LatestMajor, so payloads targeting .NET 5-10 (console or
        WinForms) resolve a compatible runtime.

    6.2.  Native Pack (PE sections)

        The payload is embedded as PE sections of a stub executable,
        keeping the .NET single-file bundle contiguous:

            [PE headers] [.stub] [bundle marker] [.lamapp]
            [bundle data] [bundle header]

        The 40-octet bundle marker (layout as 6.1) sits between .stub and
        .lamapp. The file ends with the bundle header.

        .stub   native loader section (lamarr_stub.asm). It locates the
                dotnet root (DOTNET_ROOT env -> HKLM registry -> Program
                Files), selects the hostfxr in <root>\host\fxr (payload
                runtime major preferred, else highest) and calls
                hostfxr_main_bundle_startupinfo with this exe as
                host_path and the bundle header offset.

        .lamapp Lamarr-compressed payload (main managed DLL plus all
                managed dependencies), consumed by LamarrBoot. Starting
                at offset 8, the container layout, entry semantics,
                compOff and validation are exactly those of 6.1. The
                first 8 octets are implementation-specific filler
                bytes; parsers MUST NOT interpret or validate them.

        bundle  A .NET single-file bundle whose main assembly is
                LamarrBoot. Managed dependencies are moved out of the
                bundle into .lamapp; the bundle keeps LamarrBoot,
                deps.json, runtimeconfig.json and non-managed files.
                The packer rebuilds the bundle header at end-of-file and
                rewrites the deps.json / runtimeconfig.json location
                fields (bundle version >= 2).

        .NET version compatibility: payloads targeting .NET 5-10 are
        supported. LamarrBoot defaults to net8.0-windows (Boot.csproj
        BootTfm; pass -p:BootTfm=net5.0-windows for older runtimes).
        Bundle layouts: major 2 (net5, no per-entry compressedSize) vs
        major >= 6 (net6+, compressedSize and a runtimeconfig hash
        field).

    6.3.  Host Compatibility

        The native stub targets x64 Windows (Windows 7 SP1 through
        Windows 11). It resolves only these APIs:

            ExitProcess, LoadLibraryA, GetProcAddress,
            GetModuleFileNameW, GetEnvironmentVariableW,
            FindFirstFileW, FindNextFileW, FindClose,
            RegOpenKeyExW, RegQueryValueExW,
            GetCommandLineW, CommandLineToArgvW

        RegOpenKeyExW / RegQueryValueExW come from advapi32.dll,
        CommandLineToArgvW from shell32.dll, and
        hostfxr_main_bundle_startupinfo via GetProcAddress on hostfxr.dll.

        Hardware-enforced CET (shadow stack / indirect branch tracking)
        is not handled: a system enforcing CET on non-ENDBR64 targets
        will fault. CET is opt-in on mainstream Windows 7 SP1 through
        Windows 11 deployments.

        The .NET host itself (apphost + coreclr) carries its own OS
        support policy; the stub's native compatibility does not extend
        the runtime's supported Windows versions.


7.  Security Considerations

    (a)  Distance Overflow. Validate distance <= outPos before copy.
    (b)  Length Overflow. Validate outPos + length <= dstLen.
    (c)  Resource Exhaustion. Bound output allocation (e.g., 500 MiB).
    (d)  Container Integrity. Validate magic, header, bounds.

    This format is designed for distribution of trusted payloads. It
    includes no integrity checks (checksums, MACs). Untrusted input
    SHOULD be wrapped in an external integrity layer.

Appendix B.  Implementation Notes

    B.1.  Buffer Boundary Behaviour

    The format does not require the input buffer to extend beyond
    cbIn octets. During match search, the hash function (Section 5.1)
    MAY read up to three octets past the declared input length when a
    match extends to the final octet. The values read at positions
    cbIn through cbIn + 2 are therefore undefined in the general
    case.

    Conforming encoders SHOULD provide the declared input in a
    buffer padded with one zero octet beyond cbIn, yielding
    deterministic output for all inputs.

    When such padding is used, compressed output MAY differ from
    implementations that read arbitrary memory at cbIn. This
    difference is limited to the final few compressed octets and
    has no impact on decompression correctness. Decoders are
    unaffected.

    More generally, conforming encoders are free to choose their
    own match-search heuristics, so compressed output MAY differ
    between implementations anywhere in the stream, not just at
    the end. For example, the Lamarr C# encoder limits hash-chain
    traversal to 4096 entries while the original C reference
    implementation does not; on inputs with long hash chains this
    yields different (but equally valid) compressed output.
    Decompression is unaffected by such differences.

    B.2.  Hash Table at Input Boundary

    The hash function (Section 5.1) reads a u32 at the current input
    position. When the encoder position is within 3 octets of cbIn,
    this read extends beyond the declared input buffer. In memory-
    unsafe environments the value is undefined; in memory-safe
    environments the read MUST be guarded.

    The Lamarr C# reference implementation returns hash bucket 0 for
    positions where (uPos + 3 >= cbIn). This guard is transparent
    at all input positions except the final three, where the hash
    bucket differs from implementations that read past cbIn. The
    effect is indistinguishable from the B.1 boundary behaviour.
    Compressed output MAY differ in the final few octets with no
    impact on decompression correctness.

    B.3.  Copy Chunk Octet Alignment

    The copy chunk (Section 4.3) carries an uncompressed run whose
    length is rounded down to a multiple of 8 octets. The encoded
    length is cbCopy = cbUCData >> 3, so the chunk copies exactly
    cbCopy * 8 octets, that is cbUCData rounded down to the nearest
    multiple of 8. Section 4.3 expresses the same length as C * 4
    octets, where C = 2 * cbCopy.

    When cbUCData is not a multiple of 8, the trailing octets up to
    the next multiple of 8 are not part of the copy chunk. The
    encoder MUST advance its input cursor by only cbCopy * 8 octets
    and encode the remaining octets as literals or matches in
    subsequent iterations. Advancing by the unrounded cbUCData drops
    the remainder and truncates the decompressed output, producing a
    stream the stub loader rejects as a corrupt payload.
