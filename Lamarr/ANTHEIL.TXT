在.NET单文件分发之上做方法体加密、JIT层解密与条目混淆
前置：.NET单文件 / PE / JIT基本概念

------------------------------------------------------------------------------
	〇	George Antheil与《机械芭蕾》
------------------------------------------------------------------------------

	George Antheil（1900-1959）的《机械芭蕾》（Ballet Mécanique，1923-25）配器里
	有16台自动钢琴、飞机螺旋桨、电铃和警笛等。自动钢琴由打孔纸卷（piano roll）驱动：
	纸带上的孔位决定击键时刻，乐谱被转录成孔位之后，演奏完全交给机械。这件事的本质，
	是把乐谱"编译"成机器指令

	全篇围绕一个设计：程序在磁盘为密文，运行时在JIT层现场解密，条目体系里混入诱饵。
	三者共同的效果是——静态分析得到噪音，动态分析费时费力、变得不值得破。


------------------------------------------------------------------------------
	一	前置知识
------------------------------------------------------------------------------

	三个概念：.NET单文件怎么组织、PE怎么分节、JIT在哪里读方法体。


	1.1	单文件与bundle

		dotnet publish -p:PublishSingleFile=true把主程序、依赖dll、deps.json、
		runtimeconfig.json一起塞进一个exe。内部结构是"AppHost壳 + 一串条目"。
		文件末尾有一段bundle header，记录每个条目的名字、偏移、大小、类型；入口通过
		40字节的marker（签名）从文件尾往前扫描定位。条目数据是明文的，谁都能拆出来
		——这是后面所有加密的出发点。

		另外，bundle header有版本差异：major 2（net5时代，无
		per-entry compressedSize字段）；major 6+（net6+，每条目带
		compressedSize，还多一个runtimeconfig哈希字段）。antheil重写
		bundle头时按payload的目标版本选对应布局——老工具读新bundle
		会漏字段，这是单文件格式本身的版本兼容问题。


	1.2	PE与节区

		可执行文件按节组织：.text（代码）、.rdata（只读数据）、.data（可写数据）等。
		文件里的raw offset和内存里的RVA是两套坐标，手工装载时按节映射。Antheil的
		Iamdec是个"裸dll"，靠手工映射加载。


	1.3	JIT与compileMethod

		方法体在磁盘是IL字节码，首次调用时由JIT编译成机器码。编译的必经入口是
		ICorJitInfo::compileMethod。但还有"提前偷看"的路径：内联分析（canInline）、
		Tier1预编译、OSR（栈上替换）。它们不经过compileMethod，直接读方法体——这一
		事实决定了jithook必须多守一道门。


	1.4	方法表示法：MethodDesc与方法体头

		CLR内部用MethodDesc表示一个方法，compileMethod拿到的ftn（方法
		令牌）指向的就是MethodDesc。方法体在内存/磁盘上的布局由
		COR_ILMETHOD头描述：FatHeader开头的标志、CodeSize（IL字节数）、
		MaxStack、局部变量签名令牌，以及EH区的偏移。jithook解析方法体
		就是先读FatHeader，按CodeSize和EH区信息把方法体完整拿下来，
		解密后原样交回——6.3讲的就是EH区的两种形态。

		X0伪造的那个假方法（5.4），伪造的正是MethodDesc。


	简明概念
			IL						方法体在磁盘的字节码形态
			method				方法：方法体 + 局部变量签名 + EH表
			EH表					异常处理区域表（try/catch/finally）
			compileMethod	JIT编译入口（ICorJitInfo）
			canInline			JIT问"能否内联"的回调（vtable slot 6）
			bundle				.NET单文件打包容器
			marker				40字节：8B header偏移 + 32B签名
			lamapp				自定义数据区（.lamapp节）
			LoadBare			手工映射裸PE的函数
			Tier0					快速JIT：首调不优化，启动快
			Tier1					后台优化编译：方法热了重新编译
			OSR						栈上替换：长循环原地升级编译
			R2R						ReadyToRun预编译native映像
			MethodDesc		CLR内部的方法表示（compileMethod的ftn指向）
			COR_ILMETHOD	方法体头：CodeSize/MaxStack/EH区
			AppHost				.NET单文件的原生引导壳
			hostfxr				运行时定位与加载器（dotnet host）


------------------------------------------------------------------------------
	二	为什么需要Antheil
------------------------------------------------------------------------------

		单文件解决了分发，但留下两个问题：体积和明文。体积由Lamarr压缩解决
		明文则由Antheil解决。


	2.1	明文问题

		单文件里的条目是完整IL。用ILSpy / dnSpy打开主程序，代码还原度很高；
		依赖的NuGet包也一目了然。native打包只是把IL压缩过，运行时解压成完整IL
		再交给JIT——dump内存照样能拿回原始IL。压缩挡不住静态反编译。


	2.2	思路：让明文不存在

		与其压缩明文，不如让IL明文不存在。方法体在磁盘上直接加密，JIT编译时现场解密。
		于是：
			- 静态dump文件 -> 全是密文，反编译失败
			- 内联 / Tier1 / OSR提前读方法体 -> 读到密文 -> 拦下
			- 内存里解密过的IL是临时的，编译完即弃

		这个决定把"加密"从存储问题变成了JIT层的运行时问题——这样就有了jithook。

			1. 方法体加密		MethodBodyEncryptor：写密文 + CRC32签名表
			2. JIT解密			jithook：compileMethod解密 + canInline门禁
			3. 条目伪装			Iamdec真解码器vs lamdec蜜罐 + 随机诱饵

		逆向者能拿到的完整明文只有以万行计的机器码


------------------------------------------------------------------------------
	三	宏观架构
------------------------------------------------------------------------------

	3.1	产物布局

			PE头
			.text				anthel_stub.asm入口壳（找hostfxr）
			marker 40B	8B header偏移 + 32B签名
			.rdata			.lamapp：seed/头/表/名称/4KB页数据
			bundle数据	BootAntheil + 依赖 + Iamdec + !!jhk +
									!!sig + lamdec蜜罐 + 随机诱饵
			bundle头		重建的.NET bundle header（文件尾）


	3.2	三个世界

			磁盘态：bundle条目是密文（方法体加密、seed XOR、压缩）
			内存态：BootAntheil解出主程序IL（已解密）交给JIT
			JIT态 ：jithook现场解密方法体，编译成机器码执行

			防线 = 磁盘密文 + JIT门禁 + 条目混淆。


	组件与职责
			PeWriterAntheil.cs			打包器：重写PE、组bundle、写.lamapp
			anthel_stub.asm					入口壳（native，启动CLR）
			antheil_paged.asm				Iamdec解码器（4KB页解码）
			antlion_deco.asm				z0.dll蜜罐（假gzip解码器）
			jithook.asm							JIT钩子（compileMethod + canInline）
			BootAntheil							托管引导：解析/解密/装钩子
			MethodBodyEncryptor.cs	方法体加密器
			build_asm.ps1						汇编编译 + 调打包器


------------------------------------------------------------------------------
	四	容器与条目体系
------------------------------------------------------------------------------

	4.1	条目清单

		bundle里实际是七类东西（即打包顺序）：

			BootAntheil		主程序条目，替换原主程序
			依赖dll				托管依赖，方法体已加密
			Iamdec				真解码器（antheil_paged.asm，导出名同）
			!!jhk					jithook.dll
			!!sig					CRC32签名表，每方法4字节
			lamdec				蜜罐（z0.dll，antlion_deco.asm假gzip解码器）
			*decoy*				4个随机命名/随机数据条目

		逆向者凭直觉找解码器，先撞上的是小写L的lamdec——蜜罐；真解码器叫Iamdec（大写i）
		"!!" 前缀模仿.NET内部标记，让 !!jhk / !!sig混在列表里不显眼。随机诱饵每次
		打包都不同（名字4~16个小写字母，数据64~512随机字节）。


	4.2	.lamapp区

		条目清单存在.lamapp区（PE的.rdata节）。逐字段：

			0		64B		BSJB伪头（#~ / #Strings指向诱饵区）
			64		32B	seed，ASCII，存时与KSeed异或
			96	 4B		payload FNV-1a哈希（selftest用）
			100	16B		bundle头：count/cbOrigTotal/dataOff/decoyCount
			116	20N		条目表：nameLen/rawLen/compLen/compOff
			...	...		名字区（UTF-8，4对齐）+ 数据区

		开头64字节是假metadata：伪造 #~ 和 #Strings两个stream，偏移指向诱饵区，按标准
		格式解析的工具会顺着 #~ 走进假数据。seed每次打包随机（Guid "N" 格式），两次产物
		互不相同——重打包等于整体换钥匙。bundle头四个u32都与派生key异或，直接读是噪音。


	4.3	BSJB伪头逐字节

		伪头只有64字节，按BuildFakeBsjb拼装，字节级看是：

			0		 42 53 4A 42								"BSJB" 魔数
			4		 01 00											major = 1
			6		 01 00											minor = 1
			8		 00 00 00 00								保留
			12		0C												version字符串长度 = 12
			13		00 00 00									保留
			16		76 34 2E 30 2E 33 30 33 31 39			"v4.0.30319"（12字节，到27）
			28		00 00											保留
			30		02												声明2个stream
			31		00												保留
			32		4字节											#~ 指向（诱饵数据）的偏移
			36		4字节											#~ 长度
			40		23 7E											"#~" 名字
			42		00 00											保留
			44		4字节											#Strings指向（名字区）的偏移
			48		4字节											#Strings长度
			52		23 53 74 72 69 6E 67 73		"#Strings"（8字节，到59）
			60		00 00 00 00								保留

		关键点：偏移32和44这两个字段，指向的不是真metadata，而是诱饵区（#~ 指向
		解码器假数据、#Strings指向名字区）。标准解析器走到这里，拿到的是一份"看起来
		合法、读起来是垃圾"的表。为什么这一套能骗过标准解析器：.NET工具读程序集元数据，
		第一步就是找MetadataRoot，然后按#~和#Strings两个stream的偏移去读表和字符串。
		伪头给出的是合法格式的偏移和长度，但#~指向的数据是解码器假数据（解析出来是
		乱码表），#Strings指向的名字区也不是真正的元数据字符串堆。工具按偏移读完，
		要么解析失败，要么得到垃圾——但不会因为"结构不合法"直接报错。于是逆向者得到的
		是困惑，而不是明确的失败。


	4.4	密钥派生

			KSeed = KS0A^KS0B, KS1A^KS1B, KS2A^KS2B, KS3A^KS3B
							（四个u32常量对异或，小端写16字节）
			K1		= FNV-1a：h = LK0A^LK0B，对seed逐字节
							h ^= b; h *= LK1A^LK1B
			K2		= 4元素置换：线性同余推进 + 交换，由k派生
			K3		= 逐槽key：K3(k, i)，每行独立
			LamKey / LamPerm / LamSlot是打包侧的对应实现

		seed和key的配合：seed由打包器随机生成并XOR KSeed存盘，运行时还原出真seed
		再派生全部key——所以重打包就是换钥匙，旧产物难以复用分析结论。
    
    
	4.5	设计权衡：为什么XOR不是AES

		方法体加密用的是XOR+常量派生，不是AES。两个理由：
			1. 成本：AES每次编译现场解密的开销大得多，XOR逐字节几乎免费。
					方法体可能被编译两遍（Tier0/Tier1），开销会被放大。
			2. 威胁模型：目标不是密码学强度，而是挡静态反编译和
					通用工具流水线。XOR密文足以让通用工具全部翻车。seed随机+重打包换钥匙，
						两次产物互不相同，避免固定密钥被复用。
		简单来说：密码学选型要匹配威胁模型——防君子不防小人，
		但这里的"君子"（通用工具）已经全灭了。


	4.6	解码规则

			compLen == rawLen	原样：XOR KSeed还原
			compLen < rawLen	压缩：按4KB页逐页调Iamdec


	Iamdec接口签名
			Iamdec(state 0x38B, hist 0x80000B, page 0x1000B, src)
			返回0成功；逐页调用，state / hist跨页保持。


------------------------------------------------------------------------------
	五	BootAntheil：加载链
------------------------------------------------------------------------------

	双击exe之后：antheil_stub.asm找hostfxr启动CLR，CLR按单文件机制加载主程序——
	而主程序条目里装的是BootAntheil。加载链从BootAntheil.Main开始，共六步：

			AD()							反调试：先确认环境干净
			X0()							伪造MethodDesc：给CLR一个假方法
			X1()							解析.lamapp：读seed、派生key、解表
			EnsureDecoder()		找Iamdec条目，LoadBare裸映射
			X3()							解出主程序条目（XOR或按页解码）
			W1()							注册依赖解析 + 写元数据
			最后invoke				调主程序入口


	5.1	AppHost与hostfxr：exe是怎么启动的

		.NET单文件exe的最外层是apphost——一个原生壳，不是托管代码。
		它做的事：读runtimeconfig.json定位runtime版本，加载hostfxr（dotnet的hosting
		入口），由hostfxr加载coreclr并传入托管入口。anthel_stub.asm手写复刻的正是
		这一套：遍历PEB找kernel32，解析API，找dotnet root（DOTNET_ROOT环境变量 ->
		注册表 -> ProgramFiles），选hostfxr，最后调hostfxr_main_bundle_startupinfo。
		区别是anthel_stub没有导入表，一切API都靠运行时解析。

		它怎么在"无导入表"下调用API？三件事：

			1. 从PEB（进程环境块）出发，沿PEB_LDR_DATA的InMemoryOrderModuleList
					找kernel32/ntdll基址。
			2. 在模块导出表（Export Directory）里按名字找函数，ResolveApi就是这段逻辑。
			3. 跨模块再查用ResolveApiIn（指定模块）。

		这是shellcode的基本功：位置无关代码不依赖链接器补导入表，一切API地址运行时现找。
		LoadBare加载Iamdec是同一思路——裸dll不需要导入表，因为压根没有导入。


	5.2	整体时序

	 exe启动
		 |-- anthel_stub.asm：找hostfxr -> hostfxr_main_bundle
		 |-- CLR加载bundle主程序（= BootAntheil）
		 |-- BootAntheil.Main
		 |			 |-- AD()						反调试三查
		 |			 |-- X0()						伪造MethodDesc
		 |			 |-- X1()						解析.lamapp（seed -> key -> 表）
		 |			 |-- EnsureDecoder()	找Iamdec -> LoadBare
		 |			 |-- X3()						解主程序（XOR / 按页Iamdec）
		 |			 |-- W1()						写元数据 + 注册Resolving
		 |			 -- invoke					主程序Main
		 -- 主程序运行（依赖按需从bundle解出）


	5.3	AD：反调试

		调试器是最直接的观察者，attach上来内存明文一目了然。三种手段轮着查：
		IsDebuggerPresent（本地）、CheckRemoteDebuggerPresent（远程）、
		还有NtQueryInformationProcess查调试端口。任何一种命中直接
		Environment.FailFast(null)。尽管拦不住高手，但把"随手attach"的代价抬高了。


	5.4	X0：伪造MethodDesc

		CoreCLR解析bundle时会调用主程序预设的方法入口。X0在内存拼一个最小的
		MethodDesc：栈上放几条指令（90 90 90 90 EB 00 C3 = nop*4 + jmp+0 + ret），
		再补全必要头字段，让CLR能成功调过去。它不干活，只让CLR以为这里有个方法。


	5.5	X1：解析.lamapp

		四件事：读seed异或还原；K1派生主key；K2置换 + K3逐槽派生slot key；
		按置换解开bundle头，再按20字节一条解条目表。表里有真条目也有诱饵，
		X1只解出来，不区分——区分是后面各步按名字做的事。


	5.6	EnsureDecoder与LoadBare

		EnsureDecoder在条目表里找名字等于 "Iamdec" 的条目，取出dll字节异或KSeed还原，
		LoadBare映射进内存。

		LoadBare为什么可以这么"裸"：Iamdec是自己写的dll，无导入表、无重定位、
		最重要的是位置无关。映射只需三步：

			- 读PE头，找.text / .rdata两个节
			- VirtualAlloc一块RWX
			- .text拷到基址，.rdata按RVA摆到偏移处

		返回基址直接当函数指针用。位置无关的关键：antheil_paged.asm内部只用基址相对寻址，
		不依赖任何外部符号，所以免去商业壳常见的导入表修复和重定位。


	5.7	X3：解出主程序

			compLen == rawLen		没压缩：直接XOR KSeed还原
			compLen < rawLen		压缩：按4KB一页逐页调Iamdec
		分页解码器接口固定：state（0x38字节工作区）、hist（0x80000字节历史窗）、
		page（0x1000字节输出页）、src（压缩源）。最后一页不足4KB按实际长度收尾。
		解出来是完整托管IL，但它还要依赖别的dll。


	5.8	W1：依赖与元数据

		CoreCLR单文件机制只认deps.json / runtimeconfig.json。W1做两件事：把必要
		元数据写进内存里的bundle结构让解析器认账；注册AssemblyLoadContext.Resolving
		——CLR缺哪个依赖就从bundle解出哪个（XOR或按页解码），LoadFromStream喂回去。
		之后控制权交给真正的主程序入口。


------------------------------------------------------------------------------
	六	jithook：JIT层解密与内联拦截
------------------------------------------------------------------------------

		方法体在磁盘是密文，所有要读方法体的路径都得经过解密。
		但"所有路径"这句话，是踩完坑才成立的。

		最初只钩compileMethod——编译的必经入口，在这里把IL异或回来交给JIT。
		程序能跑但跑不稳：同样的输入，有时正常，有时0x02345678，有时FailFast，
		有时访问违例。五花八门，明显指向同一个问题——还有别的路径在提前读方法体。

		顺着崩溃栈查，读者是内联分析。编译一个方法前，JIT会问"它能不能内联进来"，
		问话过程会读取被内联方法的IL——不经过compileMethod，直接从原始image拿字节，
		拿到的是密文。密文按指令解析全是垃圾，编译结果自然是错的，于是崩溃。

		解法是同时钩住canInline（ICorJitInfo vtable slot 6），对加密方法直接返回
		INLINE_NEVER：内联分析拿不到方法体，也就不会去读密文。钩完之后随机崩溃消失。


	6.1	ICorJitInfo vtable与原子安装

		JIT通过接口指针调用我们：ICorJitInfo的vtable是一张函数指针表，compileMethod和
		canInline都有固定槽位。InstallJitHook做两件事：

			1. 保存原槽位指针（解密后要调回原compileMethod）
			2. 用lock cmpxchg原子替换新指针

		原子安装不是洁癖：多线程并发编译时，如果替换写了一半就被另一个线程读到，
		vtable就是坏的，程序在启动阶段就崩。cmpxchg保证替换要么完整发生、要么没发生。


	6.2	compileMethod解密流程

			compileMethod(ftn, ...)
				sig = 查签名表(ftn)								// CRC32指纹
				if未命中:
						return原compileMethod(...)		// 非加密方法放行
				// 方法体是密文，现场解密
				分配临时缓冲（code size + EH区大小）
				IL = 方法体字节XOR jit_key				// 逐字节
				拷贝EH表:
						if small:		拷1节
						if fat:			按more_sections整块拷
												长度受dataSize上限保护
				解密后的方法体 + EH表交给JIT继续编译
				计数器++													// GetJitHookDecryptCount


	6.3	EH表：small与fat

		方法体后面跟的异常处理数据分两种：small布局只有一个节，fat布局带
		more sections计数，后面跟一整块多节数据。第一版只按small拷贝，fat方法编译时
		JIT顺着more sections去读后面的EH表——那部分根本没拷进临时缓冲，直接越界读。

		修复是区分small/fat：fat按more sections数量整块拷，并对拷贝长度加
		dataSize上限，杜绝越界。


	6.4	三条"提前读IL"的路径

		compileMethod是明面上的门，但有三条路径会绕过它直接读
		方法体：

			1. 内联分析（canInline）：编译调用方前先读被内联方法的IL。
					拦截：canInline对加密方法返回INLINE_NEVER。
			2. Tier1预编译：分层编译的快速路径，也可能触碰方法体。
					拦截：加密方法不走Tier1快速路径，或同样过签名表。
			3. OSR（栈上替换）：长循环的栈上替换需要重新编译，最终还是走编译入口，
					被compileMethod的门拦住。

		三者只要有一个拿到密文IL，编译结果就是垃圾——这就是早期"症状五花八门"的根源。


	6.5	JIT编译生命周期：一个方法被编译几次

		多数人以为方法只编译一次，实际上分层编译（TieredCompilation）会让一个方法可能被编译两遍：
			Tier0	快速JIT：首调时不做优化直接编译，图启动快
			Tier1	后台优化：方法变热后重新优化编译并替换机器码
			OSR		栈上替换：长循环在Tier0栈帧上原地升级为Tier1版本，触发一次额外重新编译

		对jithook的含义很直接：方法体解密可能被请求两次（Tier0一次、Tier1一次）。
		解密必须是幂等的——每次从密文XOR，不能解过一次就标记"已解密"然后放明文，
		否则第二次编译读到的是已经损坏的中间态。

		还有一个必须讲清的前提：R2R（ReadyToRun）。如果程序集带R2R预编译的
		native映像，JIT根本不编译该方法——方法体加密就绕过了。Antheil是安全的，
		因为打包的是普通FDD单文件，不生成R2R；加密方法体时也没有R2R版本可走。
		这一点是"磁盘密文"成立的前提。

		以及：DOTNET_TieredCompilation=0可关闭分层编译。对逆向者来说这会让
		编译路径变简单（只有一次编译），但也说明jithook的拦截点无论分层开关如何
		都是同一套compileMethod门。

		成本量级：
			- 方法体XOR：逐字节异或，整个程序的方法体也就毫秒级，
			  且只在编译时发生（每方法最坏两遍）。
			- 4KB页解码：Iamdec按页解压是主要成本，只在解主程序和
			  依赖时发生一次。
			- 启动总开销：线性、一次性，不随运行时间增长。


	6.6	MethodBodyEncryptor（打包侧）

		对每个托管dll：
			for每个方法:
					p = 方法体（FatHeader开头）
					计算code size（含局部变量签名、EH区位置）
					方法体字节XOR jit_key				// 磁盘写密文
					记录CRC32(method) 到签名表	// 供jithook匹配
		签名表整体作为 !!sig条目进bundle；密钥jit_key打包与
		运行时同一派生（Fnv1a(KSeed)）。

		为什么用CRC32：它是"指纹"不是"密钥"。jithook在编译现场只有
		MethodDesc，用指纹快速判断"这个方法被加密过没有"——查表在解密之前，
		所以签名表可以公开存在bundle里。


	6.7	诊断

		GetJitHookDecryptCount返回解密次数，用来确认钩子真的工作：selftest跑一遍
		后计数应当大于0，且解密数量与打包时输出的一致（encrypted N method bodies）。


	6.8	调试器与JIT的交互

		调试器也读IL：请求IL代码体（GetILCodeBody）、在方法上下断点（patch IL）。
		这些请求走的是调试器的通道，不经过compileMethod的解密。所以逆向者调试
		加密方法时，拿到的IL还是密文——断点打在密文上没有任何意义。这一点和反调试
		一起，构成了"动态分析也要先过密文这一关"的最后一层。


	jithook.dll导出
			InstallJitHook						改写JIT vtable
			SetJitHookKey							设置解密密钥
			AddPayloadSig							灌入CRC32签名表
			GetJitHookDecryptCount		解密计数（诊断）

	崩溃码族
			0x02345678 / 0x80000003 / FailFast / AV
				-> 内联读密文，或EH fat表漏拷


------------------------------------------------------------------------------
	七	伪装与诱饵
------------------------------------------------------------------------------

	逆向者的第一步通常是找解码器：在bundle条目里翻名字。
	既然第一步可以被预测，就让第一步走错。


	7.1	两个解码器

			Iamdec		真解码器（antheil_paged.asm）。名字像拼写错误，
								只有400行，最不像解码器。

			lamdec		蜜罐（z0.dll = antlion_deco.asm）。长达1500行
								名字最像解码器，装的却是假gzip解码器，导出
								z0_init / z0_read / z0_align / z0_size。


	7.2	随机诱饵

		打包器额外生成4个随机条目混进表里，名字4~16个小写字母；数据不是纯随机，
		而是压缩的、包含随机x64指令的合法gzip流，解压像被压缩的代码，诱导反汇编。
		整张表"内容很多"，真实目标淹没其中。

		Pheropod是整个诱饵体系的代号，包含lamdec假解码器蜜罐和gzip诱饵，
		它不试图挡住分析者，而是让其在错误目标上浪费时间。

	八	构建与验证
------------------------------------------------------------------------------

	8.1	构建命令

			dotnet publish -c Release -r win-x64 --no-self-contained
				-o ./publish -p:Packer=antheil

		流程（csproj NativeStubPack）：

			1. 主项目普通publish（Packer=none单文件）
			2. 编译LamarrNativePack（打包器）
			3. 编译BootAntheil（boot dll）
			4. build_asm.ps1：ml64编4个stub + jithook
			5. build_asm.ps1 -Pack：调打包器（带3次重试）


	8.2	build_asm.ps1

		一个脚本管到底：工具链查找（vswhere -> VCToolsInstallDir -> PATH，定位
		ml64 / link）-> 编译lamarr_stub（antheil模式再加anthel_stub /Iamdec
		以及z0三个stub）-> 编译jithook -> 带 -Pack时继续调LamarrNativePack打包

		参数：
			-AsmDir							汇编源码目录
			-OutDir							产物目录（out/）
			-Packer							antheil | native（决定编译哪些stub）
			-Pack								是否继续调打包器
			-InputPath / -Output / -Boot / -Decoder / -JitHook /
				Pheropod / -Mode		pack参数

		csproj的NativeStubPack里，编译与打包合成一个Exec调用。


	8.3	打包器视角：从单文件到Antheil产物

		PeWriterAntheil的流程：

			1. LoadStub / LoadBoot / LoadDecoder / LoadJitHook /
			   LoadPheropod / LoadPayload：读入各输入
			2. MakeSeed：生成随机seed（每次打包都不同）
			3. RebuildBundle：主程序换成BootAntheil，加密依赖方法
			   体，组装条目（Iamdec/!!jhk/!!sig/lamdec/诱饵）
			4. ComputeLayout：按节对齐重算布局
			5. PatchStubVars：替换stub模板标记（##APPNAME##等），
			   写bundle头偏移
			6. WriteFile：按布局写盘

		前文的时序图是它的"读镜像"——同一份布局，一端写、一端读。


	8.4	验证

			--lamarr-selftest		解析lamapp -> 找Iamdec -> 解主程序 
													-> FNV对比，返回0通过
			EhTestE							大EH表（11个catch）：验fat EH拷
			EhTestS							单线程：基础链路
			EhTestM							8线程并发：并发编译/解密稳定性


	8.5	工具

			cdb / windbg						抓栈、看崩溃现场（先禁用反调试）
			ILSpy / dnSp						对照打包前后
			Process Monitor					观察文件/注册表访问
			dotnet --list-runtimes	确认hostfxr环境


	8.6	阅读

			LZMAT																	Lamarr/FORMAT.TXT
			ECMA-335															方法体 / EH表规范
			CoreCLR源码jit/corinfo.h ICorJitInfo	vtable布局


	常见问题
			0x02345678 / FailFast		-> 内联读密文（canInline没装）
			EH越界									-> fat表漏拷
			selftest非0							-> Iamdec条目名不匹配或key不一致

------------------------------------------------------------------------------
	九	攻防分析
------------------------------------------------------------------------------

	9.1	攻击面

			静态：bundle条目dump、.lamapp解析、Iamdec dll提取
			动态：内存dump（解密后IL）、attach、绕过反调试
			逻辑：让canInline放行（程序自崩）、伪造签名表


	9.2	防御-绕过对照

			防线								攻击者动作				结果
			方法体密文					dump磁盘					密文，反编译失败
			反调试FailFast			attach						进程自杀
			canInline门禁				放行内联					JIT读密文 -> 自崩
			Iamdec/lamdec混淆		找解码器					拿到蜜罐z0.dll


	9.3	已知弱点

			- 反调试可被"先禁用再启动"绕过
			- 解密后的IL短暂存在于内存，窗口极小但存在
			- jithook依赖vtable槽位号，CLR大版本可能变动

		没有不可破解，只有让破解成本大于收益。目标是让静态分析基本失效、
		动态分析费时费力、大部分逆向者走三次弯路后就放弃了。
